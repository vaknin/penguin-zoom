## 1. Decisions already made (don't re-open these)

| Option | Verdict | Why |
|---|---|---|
| Reverse-engineer Zoom's protocol / write a fully native client | ❌ Rejected | Closed, encrypted protocol that changes often. Against Zoom's ToS and risks an account ban. |
| Zoom **Meeting SDK for Linux** (native C++) | ❌ Rejected | It has no built-in UI, so raw audio/video is the only way to show anything. Raw media needs host, co-host or local-recording rights, or a recording token from the host (see [Zoom's raw-recording sample](https://github.com/zoom/meetingsdk-linux-raw-recording-sample) and the [forum thread on StartRawRecording permission](https://devforum.zoom.us/t/how-to-understand-permission-issues-when-imeetingrecordingcontroller-startrawrecording-fails/117264)). In other people's meetings that means a recording prompt for the host every time. Audio and video are non-negotiable. |
| "Translate" the Web SDK into Rust | ❌ Rejected | It's closed, minified JavaScript plus a WebAssembly media engine. Porting it means reverse engineering (against the terms), and it depends on browser APIs (WebRTC, WebCodecs, WebAudio). |
| Embed Chromium (CEF, Electron, Qt WebEngine) | ❌ Rejected by owner | Too heavy, not elegant. |
| Hard dependency on Brave / opening in the default browser in app mode | ❌ Not chosen | App mode only exists in Chromium-family browsers (Firefox removed it in 2021). Kept as the **fallback** if WebKitGTK fails. |
| **Zoom Meeting SDK for Web, inside a Rust app using the system WebKitGTK webview** | ✅ **Chosen** | No bundled browser. Zoom's SDK is used as an unchanged component through bindings. Everything else is Rust. **Risks: Zoom doesn't officially support WebKitGTK, and Arch's WebKitGTK is built without WebRTC (§4.1).** The spike below exists to settle that. |

Existing projects checked (2026-11-15): there's no open-source client built on the Zoom SDK. The only project that joins real Zoom meetings is [zoom-linux-native](https://github.com/jpferraz-git/zoom-linux-native), an Electron wrapper around zoom.us/wc. A search for anyone running the Web SDK or zoom.us/wc in WebKitGTK (Epiphany, Tauri, wry) found no reports either way.

## 2. Facts that constrain the design

- **Meetings outside your own account need App Review.** Zoom: *"Apps will need to go through our App Review process to join Meetings outside their own account."* ([requirements](https://developers.zoom.us/docs/distribute/sdk-feature-review-requirements/)). Until the app is reviewed it can only join meetings hosted on the owner's own account. A ZAK does not get around this ([ZAK doc](https://developers.zoom.us/docs/meeting-sdk/auth/zak/)). That's fine for the MVP; daily use in other people's meetings needs review later.
- **Join authorization:** since 2026-03-02, joining meetings outside your own account needs a ZAK (join as the user) or an OBF token (bots only). Sources: [Zoom's FAQ on the devforum](https://devforum.zoom.us/t/updates-to-meeting-sdk-authorization-faq/139269) and [blog post](https://developers.zoom.us/blog/transition-to-obf-token-meetingsdk-apps/); the old `obf-faq` docs URL now returns 404. Inside the app owner's account, the JWT alone is enough: Zoom's [join doc](https://developers.zoom.us/docs/meeting-sdk/web/component-view/meetings-webinars/) says the ZAK is "not required if the user is in the same account as the SDK app". Plan: the user signs in with their normal Zoom account (OAuth + PKCE), the app fetches the user's **ZAK** right before each join and joins as that user (ZAK + JWT role 0).
- **Two ZAK endpoints, with different scopes** ([Users API](https://developers.zoom.us/docs/api/users/)):
  - `GET /v2/users/me/token?type=zak` needs granular scope `user:read:token` (classic `user:read`). The ZAK lasts 2 hours by default (`ttl` parameter, up to one year).
  - `GET /v2/users/me/zak` needs granular scope `user:read:zak` (classic `user_zak:read`). The ZAK expires 5 minutes after receipt.
  - Use the endpoint that matches the scope actually added to the app (see §3, owner item 5). Either works when the ZAK is fetched just before joining.
- **OAuth uses the public client (PKCE), with no secret.** Zoom's [PKCE doc](https://developers.zoom.us/docs/integrations/pkce/): turning on **Use Public Client OAuth** in the Marketplace app issues a *separate public client ID*. The token, refresh and revoke requests send `client_id` in the form body and no `Authorization` header. `code_challenge_method` must be `S256`. This also covers distribution later, since no secret is involved in sign-in.
- **Loopback redirect rules** (same doc): loopback redirects are only for the public client. Confidential clients get `Invalid redirect`. The host must be the numeric `127.0.0.1` (or `[::1]`), **not `localhost`**. Zoom ignores the port when matching, and the scheme, host and path must match. The redirect URL is saved on the public client separately from the confidential one.
- **Token lifetimes:** access tokens last 1 hour, refresh tokens 90 days. Each refresh returns a new refresh token; always store the latest one.
- **The Web SDK needs a signature for every join** (a JWT signed with the client secret; details in §4.1). This is the only use of the secret. For local use, the Rust app signs locally with the secret from the keyring. If the app is ever distributed, signing moves to a tiny hosted service (e.g. a Cloudflare Worker) and the secret never ships.
- Zoom's Linux SDK docs say the Meeting SDK is "reserved for human use cases". A personal client is exactly that.
- Web SDK: npm `@zoom/meetingsdk`, latest **6.10.0** (2026-10-23). Zoom's [SharedArrayBuffer doc](https://developers.zoom.us/docs/meeting-sdk/web/sharedarraybuffer/) says `SharedArrayBuffer` powers advanced features (720p send with WebAssembly video, among others) and is "not required for the SDK to function". It needs the page to send cross-origin isolation headers (COOP/COEP), and on WebKitGTK 2.54 it also needs an environment variable (§4.1).
- Zoom's [browser support table](https://developers.zoom.us/docs/meeting-sdk/web/browser-support/) for Safari, which is what the SDK takes WebKitGTK for: gallery view, 720p send and screen-share send are supported; virtual background and sharing computer audio are not.

## 4. Next step: WebKitGTK spike (throwaway, go/no-go)

Goal: answer **"Can Zoom's Web SDK join a meeting with working two-way audio and video inside WebKitGTK on Hyprland?"** before writing any real UI. The sharpest form of the question, after the review: **does the SDK's media work with no `RTCPeerConnection`?** (§4.1).

Suggested shape (one binary, kept small):
- **Environment:** set `JSC_useSharedArrayBuffer=1` at the very top of `main`, before GTK or any thread starts (§4.1 explains why).
- **Window:** `tao` + `wry`. Use `wry`'s Unix extension to get the underlying `webkit2gtk::WebView` and:
  - in its settings, turn on `enable-media-stream`, `enable-mediasource`, `enable-encrypted-media`, `enable-webrtc` (a no-op on Arch's build, kept for builds that have WebRTC) and hardware acceleration,
  - handle the `permission-request` signal on the `webkit2gtk::WebView` itself and allow camera, microphone and screen capture for the local page. By default WebKitGTK denies them.
  - Set the Hyprland window class with `glib::set_prgname(Some("native-linux-zoom"))` before building the event loop. tao's `with_app_id` does not set it (§4.1).
- **Local server** (tokio + axum) on `127.0.0.1:53682` only. The page and the OAuth redirect both use `http://127.0.0.1:53682`:
  - `GET /`: the spike page. Send `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp` on every response. Vendor the SDK files under `assets/` (from npm `@zoom/meetingsdk@6.10.0`) instead of loading from Zoom's CDN.
  - `GET /oauth/login`: create a PKCE verifier and challenge, redirect to `https://zoom.us/oauth/authorize?response_type=code&client_id=<public client ID>&redirect_uri=http://127.0.0.1:53682/oauth/callback&code_challenge=…&code_challenge_method=S256`.
  - `GET /oauth/callback`: exchange the code at `https://zoom.us/oauth/token` with a form body of `grant_type=authorization_code`, `code`, `client_id` (public), `redirect_uri` and `code_verifier`, and **no `Authorization` header**. Then fetch the ZAK. Keep tokens in memory.
  - `POST /api/signature`: build the Meeting SDK JWT (HS256 with the client secret; fields in §4.1).
- **Page:** the Web SDK's component view (`ZoomMtgEmbedded`), with fields for meeting number and passcode. Join with `signature`, `meetingNumber`, `password`, `userName`, and `zak` only when signed in. Don't pass `sdkKey`, which has been deprecated since v4.

JWT and PKCE are written by hand on hmac/sha2, so no jsonwebtoken or oauth2 crate is needed.

**Verified facts: Zoom (from Zoom's docs and the SDK's own `embedded.d.ts`, v6.10.0)**
- Signature JWT ([auth doc](https://developers.zoom.us/docs/meeting-sdk/auth/)): header `{"alg":"HS256","typ":"JWT"}`, signed with the client secret. Payload is `appKey` (client ID, required; there is no `sdkKey` claim in the docs), `mn` (meeting number, required on web; Zoom's sample uses a string), `role` (0 = participant, 1 = host, required on web), `iat`, `exp`, `tokenExp` (same as `exp`). `exp` must be at least 1800 s after `iat`; 48 h is the "maximum recommended". Zoom's sample uses `iat = now - 30` and `exp = iat + 2h`.
- Optional claim `video_webrtc_mode`: `0` disables WebRTC video, `1` enables it; unset lets Zoom decide. **The spike sets `0`**, because this WebKitGTK has no WebRTC. Zoom says browsers without WebRTC video fall back to WebAssembly video anyway.
- `client.join({ signature, meetingNumber: string, password?, userName, userEmail?, zak?, tk?, obfToken? })`. `sdkKey` in join is deprecated since v4, so it's left out. `zak` and `obfToken` are mutually exclusive.
- `client.init({ zoomAppRoot, assetPath?, webEndpoint?, language?, customize?, patchJsMedia?, leaveOnPageUnload? })`. `assetPath` defaults to `https://source.zoom.us/{ver}/lib/av`; self-hosting it is documented, so set it to `<origin>/sdk/lib/av`. Keep `patchJsMedia` false, because it pulls from Zoom's CDN.
- The UMD component bundle `dist/zoom-meeting-embedded-6.10.0.min.js` (the same file as `component-view.umd.min.js`) needs the vendor scripts from `dist/lib/vendor/` loaded first: react, react-dom, redux, redux-thunk, react-redux, lodash. It finds its UI files at `./ui/` relative to its own script URL.
- Zoom says component view is for desktop browsers only.
- The bundle still references Zoom hosts at run time (`source.zoom.us` for `lib/lang`, `lib/image`, `lib/audio`; `st1.zoom.us` for sounds and emoji; telemetry). The ones checked with curl send `Cross-Origin-Resource-Policy: cross-origin`, so COEP `require-corp` doesn't block them.

**Verified facts: WebKitGTK 2.54.1 on this machine (live probe: a GTK3 `WebKit2` 4.1 window loading a local page with the COOP/COEP headers)**
- **The SDK loads.** `ZoomMtgEmbedded.createClient()` works, `client.checkSystemRequirements()` returns `{audio: true, video: true, screen: true}`, `client.init()` resolves, and there are no console errors. Nothing was joined.
- **No WebRTC.** `RTCPeerConnection` is undefined even with `enable-webrtc` on. Upstream's GTK default is `ENABLE_WEB_RTC` off, and [Arch's PKGBUILD](https://gitlab.archlinux.org/archlinux/packaging/packages/webkit2gtk-4.1/-/raw/main/PKGBUILD) doesn't turn it on. No GStreamer plugin can add it at run time. The SDK's media code does call `new RTCPeerConnection` in places (data-channel transport, WebRTC video). Whether its WebAssembly and WebSocket path carries audio and video without it is unknown, and is what the spike must show.
- **Cross-origin isolation works, but `SharedArrayBuffer` needs an environment variable.** With the headers, `crossOriginIsolated` is true, yet `typeof SharedArrayBuffer` is `"undefined"`: 2.54's GLib process launcher never turns the JavaScriptCore option on ([WebKit bug 317847](https://bugs.webkit.org/show_bug.cgi?id=317847), fixed on main in September 2026, not in the 2.54 branch). With `JSC_useSharedArrayBuffer=1` in the app's environment the global exists and a buffer can be posted to a worker (probed). The SDK checks exactly `typeof SharedArrayBuffer`. This variable is an internal JavaScriptCore switch, not a supported API, so the spike keeps it behind a toggle.
- The first document the webview loads must already carry the headers. Navigating from a header-less same-origin page to a headered one left `crossOriginIsolated` false.
- **COEP `credentialless` is not supported** by WebKit (probe: `crossOriginIsolated` false; the source accepts only `require-corp`). Don't plan on it.
- `http://127.0.0.1:<port>` and `http://localhost:<port>` are both secure contexts: `getUserMedia` and `getDisplayMedia` exist on both.
- Present: WebCodecs (`VideoEncoder`/`VideoDecoder`/`AudioEncoder`/`AudioDecoder`; H.264, VP8, VP9, AV1 and Opus all report supported), `AudioWorklet`, `OffscreenCanvas` with WebGL2, WebAssembly SIMD and shared memory. Missing: `MediaStreamTrackProcessor`, WebGPU, WebTransport, and `HTMLMediaElement.setSinkId` (no speaker picker; output device follows the system).
- Default user agent: `Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/605.1.15 (KHTML, like Gecko) Version/60.5 Safari/605.1.15`. The SDK reads it as Safari 60.5, which passes its Safari version checks. Don't spoof a Chrome user agent: the SDK would turn on Chrome-only paths that need APIs WebKitGTK lacks.
- Screen capture goes through the xdg-desktop-portal ScreenCast interface and PipeWire, and is on by default (`ScreenCapture` feature). The request arrives on `permission-request` as a `UserMediaPermissionRequest` and is denied unless handled. Not exercised in the probe.

**Verified facts: crates (read in `~/.cargo/registry`)**
- wry 0.57.2: `WebViewBuilderExtUnix::build_gtk<W: IsA<gtk::Container>>(self, &W)`, `WebViewExtUnix::webview() -> webkit2gtk::WebView`. tao 0.37.2: `WindowExtUnix::default_vbox() -> Option<&gtk::Box>`, `EventLoopBuilderExtUnix::with_app_id`. `with_devtools(true)` only works in debug builds unless wry's `devtools` feature is on.
- webkit2gtk 2.0.2 has `SettingsExt::set_enable_webrtc / set_enable_media_stream / set_enable_mediasource / set_enable_encrypted_media / set_hardware_acceleration_policy / set_media_playback_requires_user_gesture`, `WebViewExt::connect_permission_request`, and `UserMediaPermissionRequest` with `is_for_audio_device` and `is_for_video_device`. **It has no safe `is_for_display_device`.** A screen-capture request is one where both are false (wry's own handler uses the same test); the raw binding exists in `webkit2gtk-sys` under feature `v2_34`.
- wry's `with_permission_handler` only passes the kind of request, not the page's origin, so the spike connects `permission-request` on the `webkit2gtk::WebView` directly and doesn't set wry's handler.
- **`with_app_id("native-linux-zoom")` is invalid.** tao passes it to `gtk::Application::new`, and GTK requires an application ID with at least one dot; this one makes the constructor return NULL. Use a valid ID such as `dev.kivan.NativeLinuxZoom`, or leave it out.
- **The application ID is not the Wayland app ID.** On GTK3, Hyprland's `class` is the program name (`g_get_prgname`), which defaults to the binary name `zoom-client`. A GTK3 probe showed `class` equal to the script name with an application ID set, and equal to `native-linux-zoom` after `set_prgname`. Not yet checked with tao itself.
- tower-http's `ServeDir` (through `mime_guess`) serves `.wasm` as `application/wasm` and `.mjs` as `application/javascript`, which is what streaming WebAssembly compilation and module workers need.

**Written (2026-11-15)** (names below are from before the rename to `penguin-zoom`, §5.2)

- Tokens (access, refresh, ZAK) live only in memory for the spike.
- Extra toggles beyond the design: `ZOOM_SPIKE_WEBRTC_MODE=0|1|unset` (the `video_webrtc_mode` claim, default `0`), `ZOOM_PUBLIC_CLIENT_ID=<id>` (until owner item 4 is done, the Sign in button is disabled), `ZOOM_SPIKE_URL=<url>` (e.g. `http://127.0.0.1:53682/?autotest=1` starts the camera/mic test on load; `?m=<link>` pre-fills the meeting). `/api/zak` tries `/users/me/zak` then `/users/me/token?type=zak`, so owner item 5 doesn't block. Links that open new windows go to the system browser. `cargo test` covers the JWT encoding and log redaction.
- Run: `RUSTC_WRAPPER=$HOME/.cargo/bin/sccache cargo run` from the repo root (it serves `web/` and `assets/zoom-sdk/` from the source tree; the page files are re-read on every request, so edits need only a reload).

**Known risks to watch in the test**
- **Media without WebRTC** (above). If the join works but audio or video doesn't, look for SDK errors that mention WebRTC or data channels before blaming capture or codecs.
- `SharedArrayBuffer` on changes which SDK code path runs. If video misbehaves with it on, retry with `ZOOM_SPIKE_NO_SAB=1` before calling a no-go.
- COEP `require-corp` blocks cross-origin images without CORP. Participant avatars were not checked. That would be cosmetic, and there is no `credentialless` to fall back to.
- Zoom's sign-in page inside WebKitGTK (Google/SSO sign-in may refuse embedded webviews). Fallback: open `/oauth/login` in the system browser, which is also what Zoom's loopback guidance describes. The callback still lands on the local server.
- NVIDIA/dmabuf rendering problems in WebKitGTK on Wayland: try `WEBKIT_DISABLE_DMABUF_RENDERER=1`.
- Screen-share on Hyprland's portal has general bug reports; none specific to WebKitGTK were found.

### 5.9 Camera freeze: cause and workaround (2026-11-17, 10:36–11:00, meeting 76270121879)

**Cause (proven, replaces the "reading" in §5.8).** WebKitGTK 2.54.1 runs its camera pipeline with base time 0 (`GStreamerCapturer::setupPipeline`), so the first camera buffer's timestamp is the time since boot (the monotonic clock, which doesn't count suspend). Its `videorate` counts from 0 and first emits one copy of that frame for every 1/30 s since boot, as fast as the CPU allows: about 1.1 million copies after 10.5 hours. Until it catches up the picture is frozen and the web process burns one to two cores. On GStreamer before 1.28 WebKit set `drop-only` on `videorate`, which hid this; from 1.28 it no longer does. Reproduced outside WebKit in 20 lines of Python (same elements, system clock, base time 0): 2 camera frames in, 697,000 out in 8 s; with `skip-to-first=true` on `videorate`, 222 in and 235 out.

**Upstream.** WebKit's main branch already sets `skip-to-first` on that `videorate` (`GStreamerVideoCapturer.cpp`, with a comment describing exactly this). It is not in 2.54.1, the newest on Arch today. Nothing to report; idea 4 in §5.8 is dropped. WebKit 2.54 has no switch away from PipeWire for cameras (always the camera portal), so idea 2 is dropped too, and idea 3 (reading the camera in Rust) wasn't needed.

**Workaround in the tree** (uncommitted, like everything else):
- `gst/camfix.c`: a 40-line GStreamer tracer plugin, `penguincamfix`. On every new element it sets `skip-to-first=TRUE` if the element is a `videorate`. It changes nothing in WebKit or Zoom.
- `build.rs` compiles it with `cc` and `pkg-config gstreamer-1.0` into `$OUT_DIR`; `src/main.rs` (`install_camfix`) embeds the `.so`, writes it to `$XDG_RUNTIME_DIR/penguin-zoom/gst/` and adds `GST_PLUGIN_PATH` and `GST_TRACERS=penguincamfix` to the environment, which the web process inherits. `PENGUIN_NO_CAMFIX=1` turns it off.

### 5.11 WebKit root cause and pull request; audio both ways; more live checks (2026-11-17, 11:50–12:40, meetings 78016278397)

**One cause behind both playback faults of §5.10, and it is WebKit's** (a subagent traced it; I checked its source claims on main and re-ran its reproduction).
- `MediaPlayerPrivateGStreamer::isMediaStreamPlayer()` uses `m_source`, else `m_url`. `load()` creates the pipeline before it sets the URL, so while the pipeline is created a camera player answers "no". Two checks meant to skip camera players then run:
  - `createVideoSink()` turns QoS on for the sink (added to WebKit in December 2025, in 2.52 and 2.54; 2.50 doesn't have it). Camera buffers arrive with a decode timestamp later than their presentation timestamp by the capture latency (about 53 ms here); the sink reports the first, the converters compare the second, and every other frame is skipped. This corrects §5.10's "pipeline latency" wording. GStreamer 1.28 changed nothing relevant.
  - `managePlayerSuspend()` marks the muted, not-yet-visible player as suspended, and nothing resumes a camera player.
- Reproduced without WebKit (`appsrc do-timestamp ! videoconvert ! queue ! appsink sync=false qos=true`): 89 frames in, 89 out at 20 ms latency, 45 out at 53 ms, 89 out at 53 ms with QoS off.

Stated in the PR: **not built, no layout test**, verified by our two workarounds and the reproduction.
- **Needs the owner:** WebKit wants a bugs.webkit.org entry for every change. I have no Bugzilla account to file one; the commit message says "Need the bug URL (OOPS!)". File a bug there (the PR text can be pasted), then the bug number goes into the commit message and the PR can leave draft.

### 5.12 Phone-side frame rate: mostly a measuring fault; Zoom sends 640×360 at 27 a second (2026-11-17, 12:45–13:25, meeting 78382577039)

- **Other distros (not urgent; noted 2026-11-17).** The app itself isn't Arch-specific (Rust + WebKitGTK 4.1, GStreamer, PipeWire/Pulse, libsecret, `xdg-open`, all on every major distro). Only the install route is: `packaging/PKGBUILD` needs `makepkg`/`pacman`, so the README and `AGENT-INSTALL.md` say "Arch only". What differs elsewhere: package names (`libwebkit2gtk-4.1-0` on Debian/Ubuntu, `webkit2gtk4.1` on Fedora; GStreamer split differently), codecs (`gst-libav`/`-bad`: RPM Fusion on Fedora, explicit `-bad`/`-libav` on Ubuntu, else no video), Rust ≥ 1.85 (Debian stable / Ubuntu LTS repos may be older → rustup). Hyprland-only bits fail quietly elsewhere: `raise_window` (`hyprctl`, `src/server.rs`) does nothing on GNOME/KDE, and `packaging/hyprland.lua`; screen share works through any desktop's xdg-desktop-portal backend. Options, cheapest first: (1) an "Other distros" section in `AGENT-INSTALL.md` (deps for Debian/Ubuntu and Fedora, `cargo build --release`, `scripts/fetch-sdk.sh`, copy files as `package()` does), then drop "Arch only" from the README; (2) AUR once released; (3) Flatpak (needs a runtime with WebKitGTK 4.1, SDK fetched at build). Never tested off Arch.
- Upkeep: Zoom raises the minimum SDK version quarterly (first weekend of November, February, May and August) and aims to support each version for at least nine months ([policy](https://developers.zoom.us/docs/meeting-sdk/minimum-version/)). The Web minimum is 4.0.0 through February 2027, so 6.10.0 has plenty of room. Bump and re-test a couple of times a year, and re-vendor `lib/av` with every bump.
